# 飞书文档 + 多维表格（PRD 与需求管理）

## 什么时候用
- 国内团队写 PRD、评审纪要、上线 checklist：飞书文档（图谱 P-01 原有工具）。
- 需求池、版本规划、Bug 跟进、上线排期这类「结构化清单」：飞书多维表格（官方定位「AI 驱动的表格与业务系统搭建平台」）。
- 团队没有 Jira，或 Jira 只管研发任务、产品侧需要更灵活的视图时。

## 关键做法
- 需求池建表：需求编号、标题、来源、优先级、状态、负责人、目标版本、PRD 链接、关联 Bug；状态用单选字段，便于看板视图。
- 用多个视图分角色看：看板（按状态）、甘特（按版本排期）、表单（收集业务方需求）。
- 自动化流程：状态变「待评审」时自动通知评审人；上线后自动提醒数据回收。
- PRD 用飞书文档写，Markdown 仍是唯一真源时（如 /pm 流程），飞书只做发布与评论入口，避免两边各改一份。
- 需要和研发系统打通时用开放 API（app / table / view / record / field 资源模型），批量写入单次最多 1000 条、整批成功或失败。

## 常见坑
- 单个多维表格限制：字段 300 个（公式字段 100 个）、视图 200 个、数据表 + 仪表盘合计 100 个，大表要按版本或业务线拆分。
- 同一个多维表格同时多路写入容易冲突，官方建议同一时间只发一个写请求。
- 权限默认偏宽，涉及未发布需求要开高级权限（自定义角色最多 30 个）。
- 文档里的截图、原型链接易过期，评审版本要导出留档。

## 迁移
- 从 Excel 需求表迁移：直接导入，再把「状态 / 优先级」改成单选字段、负责人改成人员字段。
- 从 Jira 迁移不是必须：研发侧继续 Jira，产品侧多维表格通过 API 或自动化同步关键字段。

## 最佳做法
- 判断理由：国内主流协作套件，开放平台文档齐全，定「采用」；海外团队用 Lark 版本，按数据驻留要求评估，定「试用」。
- 合规：涉及用户个人信息的反馈表要做脱敏，权限按最小可见范围设置。
