## 灰度计划 <!-- 必填 -->
**放量机制**：签到的唯一入口是 Android 客户端，所以对真实用户的「比例」由应用市场分阶段发布的百分比决定；服务端另有两道闸：网关白名单（G0、G1 用）和关闭开关（任何时候可用）。应用市场的分阶段比例是「可更新用户的比例」，实际触达的用户比例会更低（更新有延迟），所以**判据以绝对请求数为准，不以日历时间为准**。

**共用观察规则**
- 每档观察期内必须至少包含：一次北京时间 00:00 跨天、一次 01:00 的对账运行。
- 低流量统计不可靠：按比例算的判据要求窗口内累计签到请求 ≥ 1000，不够就延长观察，不能因为「一个错误都没有」就放。早期按绝对值判：窗口内 5xx ≤ 2 条且逐条有结论。
- 进入下一档的所有判据必须**同时**满足，并由总控确认；只要有一条不满足，**暂停（hold）**，不自动放，也不自动回滚；回滚有单独的触发条件。
- 放量动作只在「上线窗口」的时段内做，且每次放量后值班人至少守满 2 小时。

| 批次 | 比例 / 范围 | 观察时长 | 放量判据（进入下一档，需同时满足） |
|---|---|---|---|

| G1 内部 / 种子 | Android 内测包，公司员工与种子用户 ≤ 500 人，网关白名单 | **≥ 72 小时**（必须覆盖首签第 3 天的连签奖励真实数据；第 7 天奖励见下方 G4 门槛） | 5xx 与锁超时 = 0（允许 ≤ 2 条且逐条有结论）；每次对账为空，第 3 天的 +10 奖励流水金额与余额一致；客户端「结果不明」路径（弱网 / 断网）人工走通且无多发；Android 无崩溃上升；无资金类反馈 |

| G4 市场 20% | 20% | ≥ 48 小时，跨一个完整的早高峰 | 同 G3；**积分日发放量不超过日预算阈值（B7 给出）**；锁超时 = 0 |
| G5 市场 50% | 50% | ≥ 48 小时，且**首批种子用户已走完周期第 7 天**（+30 奖励真实数据）后才可放全量 | 同 G4；第 7 天奖励流水与对账一致；容量按真实 QPS 重估，确认 2 个实例够用或先扩容 |
| 全量 | 100% | 保留关闭开关与加强值班 7 天，4 周后校准 | 稳定后撤销「加强值班」；SLO 阈值、容量、日预算按真实数据重定 |

**暂停与回滚的区别**
- 暂停：判据不满足但没有用户受损（例如样本不足、P99 略超）。动作：停在当前档，找原因。
- 回滚：满足「回滚方案」里的任一触发条件。动作：先关开关止血，再决定是否回滚代码，同时暂停 Android 分阶段发布。

## 功能开关 <!-- 必填 -->
**目标**：服务端能在分钟级一键关闭「签到入口 + 发分」，且余额、流水仍可查看。积分写入只有 `POST /api/v1/checkin` 一条路径，所以关掉它就等于关掉发分。

**现状（核对过代码）：服务端没有任何功能开关。** `main.go` 只有 5 个环境变量，没有 `CHECKIN_ENABLED`；契约里的 `CheckinStatus` 也没有「功能已关闭」的字段。因此分两层：

| 层 | 做法 | 耗时 | 是否要改代码 | 副作用 |
|---|---|---|---|---|
| SW-1 网关层（现在就能准备） | 预先写好并评审一份「关闭签到」的路由变更：`POST /api/v1/checkin` 由网关直接返回统一外壳的 503：`{"code":"service_unavailable","message":"","data":null}`（带外壳，客户端按 A2 视为「事务已回滚」，toast「签到失败，请重试」并换新 id，不会进入重发确认）；`status`、`balance`、`ledger` 继续转发 | 目标 ≤ 5 分钟（要靠 G0 的演练实测） | 不要 | 用户会看到「签到失败」而不是「功能维护中」，体验差但安全；已发积分不动。直接响应或路由权重是网关实现自带的能力，标准 Gateway API 本身不一定支持，具体实现未核实 |
| SW-2 服务端环境开关（建议补，交后端） | 新增 `CHECKIN_ENABLED`（默认 `true`）：为 `false` 时 `POST /api/v1/checkin` 在鉴权之后直接返回上述 503 外壳，不进事务；修改 env 要滚动重启 2 个实例，约 1–2 分钟 | 1–2 分钟 | **要**，属于后端工程师，需补单测 | 与 SW-1 效果相同，作为网关之外的第二道闸，网关配置出错时有用 |
| SW-3 客户端隐藏入口（待拍板） | 在 `CheckinStatus` 里**向后兼容地新增**一个字段，例如 `feature_state: "enabled" \| "disabled"`，客户端读到 `disabled` 就隐藏入口或显示「维护中」 | — | **要**，改契约（只加不改，客户端本来就要求 `ignoreUnknownKeys`），Android 还没实现 | 体验最好；契约已锁定，增补要架构师确认并走拍板，见待拍板第 2 项 |

**规则**
- 开关只管「新增发分」，**不回收已发积分**；关闭期间重放同一个 `request_id` 也不处理（直接 503），客户端等恢复后再确认。
- 打开 / 关闭开关由值班 SRE 执行，决定权在总控 / 用户；P0 资金类事件需要用户**预先授权**值班先止血再汇报（见待拍板第 3 项），否则就要等用户在线确认。
- 开关状态必须在看板上有一个醒目的标记，并写进发布日历，避免「关了没人记得」。
- **B3 / G0 的验收包含开关演练**：关、验证外壳和客户端表现、开、验证恢复，记录每步耗时。

## 回滚方案 <!-- 必填 -->
**原则**：积分是资产，回滚的对象是「入口和代码」，**不是数据**。已发出的积分一律不回收、不删除、不修改；表和流水保留。

**触发条件（任一满足就执行止血，不等例会）**
| 触发 | 级别 | 先做什么 |
|---|---|---|
| 对账 C1–C4 任一非空且确认是真实的多发 / 漏发 / 余额不一致 | P0 | 关发分开关（SW-1），冻结放量，保留现场，不动数据 |
| 签到 `5xx` 的 1 小时燃烧率超过 14.4 倍并持续（见 A-01）、或签到成功率 < 99% 持续 10 分钟 | P0 | 暂停放量；10 分钟内无明确原因且仍在烧，关开关，再决定回滚代码 |
| 503（DB 不可用 / 锁超时）占比 > 5% 持续 5 分钟 | P0 | 同上，同时检查 DB |
| 发现 header 伪造成功，或绕过网关能直连服务 | P0（安全） | 立即在网关摘掉全部路由（不只是签到），查访问日志找受影响的 user_id |
| 积分日发放量达到日预算的 100%（B7 定值） | P1 | 暂停放量，提请总控 / 用户决定是否关发分 |
| 触发器被触发（有人尝试 UPDATE / DELETE 流水）、余额出现负数 | P0 | 关开关，查来源账号，吊销该账号权限 |

**回滚步骤（均为待用户确认后执行；顺序从轻到重）**
1. **关入口（SW-1，最先做）**：应用预先评审过的「关闭签到」路由变更，验证 `POST /api/v1/checkin` 返回 503 外壳、`GET status / balance / ledger` 仍为 200。
2. **暂停 Android 放量**：在应用市场控制台暂停分阶段发布（halt）。已安装的用户无法撤回，只能靠第 1 步止血。
3. **回滚后端代码（需要时）**：
```
# 待用户确认后执行
kubectl -n <ns> rollout undo deploy/checkin-points          # 回到上一个修订版本
kubectl -n <ns> rollout status deploy/checkin-points --timeout=180s
# 首次发布没有「上一版」：改为 kubectl -n <ns> scale deploy/checkin-points --replicas=0，
# 并保持网关路由摘除（回到 S2 之前的状态），表和数据保留
```
4. **不回滚数据库。** 迁移只新增表，代码回滚后表闲置即可，没有任何兼容问题。
5. **回滚后复核**：重跑一次对账（四项）、核对余额与流水之和；写事故记录，在 08-监控告警.md 的 RB 里补条目。

**迁移 down 的风险说明（`0001_init.down.sql`）**
- 内容是 `DROP TABLE points_ledger / checkin_record / points_account` 加 `DROP FUNCTION`，**会永久删除全部积分流水和余额**。触发器只挡行级 UPDATE / DELETE，挡不住 DROP。
- 允许执行的唯一前提：**灰度前、表里没有真实用户数据**。执行前必须同时满足：`SELECT count(*) FROM points_ledger` 与 `checkin_record` 都为 0（G0 冒烟账号产生的数据也算，有就不能 down）、已有备份、用户**明确确认**。只有 DDL 账号能执行，应用账号无权限。
- G0 之后一律不执行 down。要改表结构只能走「新增迁移（additive）向前修」，例如 `0002_*.up.sql`。
- 一旦有真实发放就禁止 DROP；确实要清理环境，走单独的、经用户确认的方案，不在本上线单范围。

**已发积分的处理原则**
- 不自动回收、不修改流水。如果确认错发，只能由业务方、财务、产品评审后，走**补偿流水**（`ADJUST` 类型，数据库预留，本期没有入口）；因为有 `balance >= 0` 约束和只追加触发器，补偿要另出方案（含 SQL 评审、备份、对账复核），由用户确认后执行，本期不预先授权任何手工改账。
- 对用户的口径由产品与客服统一，不由 SRE 对外说明。

**预计耗时**：关入口 ≤ 5 分钟（目标，G0 演练实测后写回）；暂停 Android 放量 ≤ 5 分钟；后端代码回滚 ≤ 10 分钟；数据库不回滚。

## 经验条目（供复盘回流技能包）
- 踩坑：「功能开关」在 05 方案里没有设计，到 08 才发现服务端没有开关、契约也没有字段。以后方案模板要求写「如何一键关闭」，并在 05 评审时检查。
- 踩坑：只追加的流水表意味着**冒烟数据删不掉**，上线单要提前规定测试账号和金额，而不是上线后想清理。
- 更好的做法：放量判据用「累计请求数」而不是只用「时间」，早期流量小，99.9% 的比例没有统计意义；并且把「首签第 3 天、第 7 天奖励」这类要等几天才出现的真实数据写进观察期。
- 更好的做法：DB 迁移只做新增、不改存量，代码回滚就不需要迁移回滚；`down` 脚本在有真实数据后禁用。
- 更好的做法：信任网关注入 header 的服务，要有持续的伪造探针告警，而不是只在上线时验一次。
