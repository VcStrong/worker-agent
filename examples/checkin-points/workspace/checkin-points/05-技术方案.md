## 背景与决策 <!-- 必填 -->
**上下文**：积分是用户资产，护栏要求「错发 = 0、余额 = 流水之和」。签到要能扛住连点、重试、多设备并发和跨零点。目前仓库里没有任何代码，本机也没有 Go 工具链。

| # | 决策 | 备选方案 | 选择理由 | 后果 |
|---|---|---|---|---|
| D1 | HTTP 层用 Go 标准库 `net/http`（1.22+ 的 `ServeMux` 方法加路径路由）和 `log/slog`，不引入 Web 框架 | Gin / Echo / chi | 4 个接口用标准库就够；零第三方依赖，离线也能编译；没有框架升级负担 | 中间件（鉴权、限流、recover、日志）要自己写，大约 150 行 |
| D2 | 防重以 PG 唯一约束 `(user_id, checkin_date)` 为准；事务里先 `SELECT … FOR UPDATE` 锁住该用户的 `points_account` 行，把同一用户的签到串行化 | ① SERIALIZABLE 隔离级别加重试；② 乐观锁 version 字段；③ Redis 分布式锁 | 行锁只影响同一个用户，没有竞争热点；隔离级别用默认的 READ COMMITTED 就行；唯一约束是最后一道兜底，不依赖额外中间件 | 同一用户的并发请求排队，单次事务约 5–10 ms，可以接受 |
| D3 | 余额落在 `points_account.balance`，和流水在同一个事务里更新；流水只追加（触发器加数据库权限双重保证） | 每次查询时实时 `SUM(amount)` | 余额读取是 O(1)；流水量增长后 SUM 会越来越慢 | 余额和流水可能不一致，靠每日对账 SQL 兜底（US-11） |
| D4 | 幂等键 `request_id` 存在 `checkin_record` 上，加唯一约束 `(user_id, request_id)`，不单独建幂等表 | 单独的 idempotency_key 表，或 Redis SETNX | 只有签到这一个写接口，一张表就能闭环；跨零点重试（第 D 天发出、第 D+1 天才重试）也能找回原结果 | 以后有别的写接口时再抽通用幂等表 |
| D5 | 「今天」由应用层的可注入时钟算：`time.Now().In(UTC+8)` 取日期，作为参数写入 `checkin_date`；时区用 `time.FixedZone("Asia/Shanghai", 8*3600)` | PRD R1 原写法 `DATE(now() AT TIME ZONE 'Asia/Shanghai')` 由数据库计算 | 语义和 R1 一致（都以服务端收到请求的时间为准）；时钟可注入，跨零点、断签、第 7 天都能写单测；内存实现和 PG 实现结果一致；中国大陆没有夏令时，固定偏移不依赖容器里的 tzdata | 应用服务器必须开 NTP（SRE 在 08 列为检查项）；`created_at` 仍用数据库 `now()`，两者偏差只有毫秒级 |
| D6 | 流水用游标分页，游标是 `(created_at, id)` 编码成的不透明字符串 | offset / limit | 和 PRD R7 一致；有新流水插入时不会重复或漏条 | 不支持跳页，本期也不需要 |
| D7 | 存储层抽象成接口：内存实现用来自测，默认就编译；PG 实现放在 build tag `pg` 后面，再加迁移 SQL | 只做 PG 实现 | 本机没有 PG 和 Go 模块缓存，默认构建只用标准库，离线可编译；业务逻辑只写一份 | PG 实现要在有网、有 PG 的环境里跑 `go test -tags pg` 补测 |
| D8 | 奖励规则做成带版本的配置文件 `rules.json`（`rule_version`、`effective_date`、`base_points`、`streak_bonus[7]`）；启动时加载，按「生效日 ≤ 今天的最新版本」选用 | 存数据库配置表或配置中心热更新 | PRD R5 要求改配置按上线变更走、不能热改；放文件里可以走 Code Review | 改数值要发版；`effective_date` 填下一个北京时间 00:00 所在的日期 |

## 架构与模块 <!-- 必填 -->
```
Android App ──HTTPS──> API 网关（Gateway API：校验 token，剥掉客户端自带的 X-User-*，注入 X-User-Id / X-User-Status，按用户限流）
                           │ 内网 HTTP
                           ▼
                  checkin-points 服务（Go）
                  ├─ httpapi：路由、中间件（recover → accesslog → auth → ratelimit[仅 POST]）、DTO、错误码
                  ├─ service：签到用例（判日、连签计算、幂等、发分），状态预览，余额，流水
                  ├─ rules：奖励规则配置（版本化）+ 纯函数 CalcCycleDay / PointsFor
                  ├─ clock：可注入时钟（UTC+8）
                  └─ store（接口）── memory 实现（自测）/ postgres 实现（-tags pg）
                           │
                           ▼
                     PostgreSQL 18：points_account / checkin_record / points_ledger
                           ▲
                  每日 01:00 对账任务（scripts/reconcile.sql，由 CronJob 跑 psql），有异常就告警
```

**签到事务流程**（`POST /api/v1/checkin`，READ COMMITTED，`lock_timeout=2s`、`statement_timeout=3s`）：
1. `today := clock.Now().In(UTC+8)` 取日期；`rule := rules.Effective(today)`。
2. `BEGIN`
3. `INSERT INTO points_account(user_id) VALUES ($1) ON CONFLICT DO NOTHING;` 然后 `SELECT balance FROM points_account WHERE user_id=$1 FOR UPDATE;`（加锁顺序固定为先锁账户行，避免死锁）
4. 按 `(user_id, request_id)` 查 `checkin_record`：命中就**原样重放**那条记录的结果，业务码 `ok`，`ROLLBACK` 后返回（覆盖超时后用同一个 request_id 重试，包括跨零点重试）。
5. 按 `(user_id, checkin_date=today)` 查：命中就返回 `already_checked_in` 和当天的发放明细，然后 `ROLLBACK`。
6. 查最近一条签到：`SELECT checkin_date, streak_days FROM checkin_record WHERE user_id=$1 AND checkin_date < $today ORDER BY checkin_date DESC LIMIT 1`；如果它的日期 = today−1，`streak = last.streak_days + 1`，否则 `streak = 1`；`cycle_day = (streak−1) % 7 + 1`；`base = rule.base_points`，`bonus = rule.streak_bonus[cycle_day−1]`。
7. `INSERT checkin_record … RETURNING id`。万一撞上 `23505`（理论上被第 3 步的行锁挡住了，这里是兜底）：`ROLLBACK`，然后按第 4、5 步重新查一次再返回。
8. `INSERT points_ledger`：一条 `CHECKIN_BASE`（`balance_after = balance + base`）；`bonus > 0` 时再插一条 `CHECKIN_STREAK_BONUS`（`balance_after = balance + base + bonus`）。
9. `UPDATE points_account SET balance = balance + $total, updated_at = now() WHERE user_id=$1`
10. `COMMIT`。提交成功后才打 `checkin_success` 和 `points_grant` 两条 slog 事件（`event` 字段），由日志采集送到神策。如果进程在提交之后、打日志之前崩溃，事件会丢；数仓可以用 `checkin_record` / `points_ledger` 表回补，口径上以表为准。

**状态计算**（`GET /api/v1/checkin/status`，不加锁）：先取今天的记录，再取 today 之前最近的一条记录。
- 今天已签：`streak_days` 和 `cycle_day` 取今天那条记录的值；格子 1..cycle_day 标为已签，今天那格 `is_today=true`。
- 今天未签，且最近一次是昨天：`streak_days` = 昨天的值（例如 3，对应文案「已连续签到 3 天」）；今天的 `cycle_day = streak_days % 7 + 1`；格子 1..cycle_day−1 标已签。
- 今天未签，且最近一次早于昨天：`streak_state=BROKEN`，`streak_days=0`，`cycle_day=1`，格子全部未签。
- 从没签过：`streak_state=NONE`，`streak_days=0`，`cycle_day=1`。
- 昨天正好是周期第 7 天：今天 `cycle_day=1`，格子全部清空（对应交互说明「第 8 天格子重置」）。

## 接口契约 <!-- 必填 -->
**通用约定（锁定）**
- Base path `/api/v1`，JSON 用 UTF-8，字段名统一 snake_case。只允许**向后兼容的新增**：客户端必须 `ignoreUnknownKeys = true`，枚举遇到未知值要走兜底分支。
- 统一响应外壳：`{"code": string, "message": string, "data": object|null}`。`message` 只用于日志和排查，客户端**不展示**，文案以交互说明为准。
- 时间：`created_at` 等时刻字段用 RFC 3339 UTC 格式（`2026-11-14T01:12:00.123456Z`），客户端按北京时间格式化成 `yyyy-MM-dd HH:mm`；日期字段（`checkin_date`、`server_date`）是北京时间日期，格式 `yyyy-MM-dd`。
- 整数：积分、余额都是 JSON number（int64，Kotlin 用 `Long`）；`id`、`biz_id` 用 **string**，避免以后 Web 端遇到 2^53 精度问题。
- **鉴权**：MVP 由网关注入 `X-User-Id`（1–64 位 `[A-Za-z0-9_-]`），缺失或格式不对一律 401；`X-User-Status`（`active` | `banned` | `deactivating`，缺省视为 `active`）。**正式环境**由网关校验 App 的登录 token（`Authorization: Bearer …`），校验通过后注入这两个 header，并且**必须剥掉客户端自己带上来的同名 header**；服务只监听内网，不对公网暴露。本服务不解析 token。
- 每个响应都带 `X-Trace-Id`（链路追踪用）。它和幂等用的 `X-Request-Id` 是两回事，网关不能改写 `X-Request-Id`。

**`CheckinStatus`**
| 字段 | 类型 | 说明 |
|---|---|---|
| `server_date` | string `yyyy-MM-dd` | 服务端算出的北京时间「今天」；客户端用它判断是否跨天，不用本地时间推算 |
| `timezone` | string | 固定 `"Asia/Shanghai"` |
| `checked_today` | bool | 今天是否已签 |
| `can_checkin` | bool | `!checked_today && account_status == "active"` |
| `account_status` | string enum | `active` / `restricted`（403 场景；签到按钮置灰，文案「账号状态异常，暂无法签到」） |
| `streak_state` | string enum | `NONE`（从没签过，文案「每天签到领积分」）/ `ACTIVE` / `BROKEN`（「连签已中断，今天重新开始」） |
| `streak_days` | int | 已签：含今天；未签且连签未断：截至昨天的天数；`NONE` / `BROKEN` 时为 0 |
| `cycle_day` | int 1–7 | 已签：今天那条记录的周期天数；未签：今天如果签到会是第几天 |
| `today_points_preview` | int | 未签：今天能拿到的合计（10 / 20 / 40）；已签：今天实际拿到的合计 |
| `tomorrow_points_preview` | int | 假设今天签了、明天继续签，明天能拿的合计（P1 的「明天 +N」） |
| `rule_version` | string | 当前生效的规则版本，例如 `"v1"` |
| `cycle` | array[7] of `CycleCell` | 本周期 7 个格子 |

`CycleCell`：`{"day": int 1–7, "points_total": int, "bonus_points": int, "checked": bool, "is_today": bool}`。`points_total` 已签的格子取记录里的实际值，其余取当前规则的值（R5：规则变更当天已签的格子不变）。

**`LedgerItem`**：`id` string，`type` string enum（`CHECKIN_BASE` / `CHECKIN_STREAK_BONUS`；预留 `REDEEM` / `ADJUST` / `EXPIRE`，客户端遇到未知类型显示 `remark`，`remark` 为空时显示「积分变动」），`amount` int64（有符号），`balance_after` int64，`biz_type` string，`biz_id` string，`remark` string，`created_at` string（RFC 3339 UTC）。排序为 `created_at DESC, id DESC`；同一个事务里的两条流水时间相同，奖励那条排在基础那条上面。

**游标**：`next_cursor` 是 base64url（不带 padding）编码的 `"<created_at 的 Unix 微秒>_<id>"`，**对客户端不透明**，原样回传即可。没有更多数据时 `has_more=false`，`next_cursor=null`。

**错误码表**
| HTTP | `code` | 场景 | 客户端处理（对照交互说明） |
|---|---|---|---|
| 200 | `ok` | 成功；同一 request_id 重放 | 签到：toast「签到成功 +N 积分」 |
| 200 | `already_checked_in` | 今天已用别的 request_id 签过（连点、另一台设备） | 当成功处理，显示「今日已签到」，不弹 toast |
| 400 | `invalid_request` | 缺少 X-Request-Id 或不是 UUID；limit 越界 | 属于客户端 bug：按「签到失败，请重试」处理并上报 |
| 400 | `invalid_cursor` | 游标解不开 | 从第一页重新拉 |
| 401 | `unauthorized` | 没有 X-User-Id 或格式不对（网关 token 校验失败也是 401，由网关返回） | 跳登录页，回来后刷新，不自动签到 |
| 403 | `account_restricted` | `X-User-Status` 是 banned / deactivating，且请求的是签到 | 按钮置灰，显示「账号状态异常，暂无法签到」 |
| 404 | `not_found` | 路由不存在 | 上报 |
| 405 | `method_not_allowed` | 方法不对（ServeMux 自动返回，外壳由中间件统一包装） | 上报 |
| 429 | `rate_limited` | 超过 10 次/分钟；响应头带 `Retry-After` | toast「操作太频繁，请稍后再试」，按钮恢复 |
| 500 | `internal_error` | 未预期的错误（事务已回滚） | toast「签到失败，请重试」；生成新的 request_id |
| 503 | `service_unavailable` | 数据库不可用、拿锁超时、服务端 5 秒处理超时 | 同 500；签到场景如果客户端先触发了 10 秒超时，走 CONFIRMING 流程 |

**超时约定**：客户端签到 `callTimeout = 10s`；服务端 handler `context` 超时 5s，`http.Server` 设置 `ReadHeaderTimeout = 5s`、`WriteTimeout = 8s`；数据库 `statement_timeout = 3s`、`lock_timeout = 2s`。服务端一定比客户端先放弃，所以客户端超时后再查状态，看到的就是最终结果。

回滚策略：down 脚本**只能在灰度前、表里没有真实用户数据时**执行。一旦有真实发放，**禁止 DROP**（积分是资产）。上线后要回滚就把服务下掉，或在网关摘掉路由、客户端隐藏入口，表和数据保留。DROP 属于删除数据库操作，必须用户确认后才能执行。

**一致性与并发**
- 防重有三层：① 客户端在请求中禁用按钮；② `request_id` 幂等；③ `uq_checkin_user_date` 唯一约束（最终依据）。另外 `uq_ledger_biz` 防止同一条签到记录被发两次分。
- 同一用户的写操作靠 `points_account` 行锁串行；不同用户之间没有锁竞争。不用 SERIALIZABLE，不需要重试循环。
- `CHECK (balance >= 0)`：以后有积分消耗时，扣成负数会直接失败。

**时区处理**
- 存储：所有时刻用 `TIMESTAMPTZ`（UTC）；`checkin_date` 用 `DATE`，含义是北京时间日期。
- 计算：应用层用 `UTC+8` 固定偏移算「今天」和「昨天」（D5），不依赖数据库会话时区和容器 tzdata。
- 展示：客户端拿到 UTC 时刻后用 `ZoneId.of("Asia/Shanghai")` 格式化，不用设备时区。

**每日对账 SQL（`server/scripts/reconcile.sql`，每天 01:00 跑；结果非空就告警，并记进护栏指标）**
```sql
-- C1 余额 ≠ 流水之和（包括有流水但没有账户的情况）
SELECT COALESCE(a.user_id, l.user_id) AS user_id, a.balance, l.sum_amount
FROM points_account a
FULL JOIN (SELECT user_id, SUM(amount) AS sum_amount FROM points_ledger GROUP BY user_id) l USING (user_id)
WHERE COALESCE(a.balance, 0) <> COALESCE(l.sum_amount, 0);

-- C2 同一用户同一北京时间日期，基础奖励超过 1 条
SELECT user_id, (created_at AT TIME ZONE 'Asia/Shanghai')::date AS d, COUNT(*)
FROM points_ledger WHERE type = 'CHECKIN_BASE'
GROUP BY 1, 2 HAVING COUNT(*) > 1;

-- C3 签到记录和流水金额对不上（漏发、多发）
SELECT c.id, c.user_id, c.points_base + c.points_bonus AS expected, COALESCE(SUM(l.amount), 0) AS actual
FROM checkin_record c
LEFT JOIN points_ledger l ON l.biz_type = 'CHECKIN' AND l.biz_id = c.id::text
WHERE c.checkin_date = (now() AT TIME ZONE 'Asia/Shanghai')::date - 1
GROUP BY c.id, c.user_id, c.points_base, c.points_bonus
HAVING c.points_base + c.points_bonus <> COALESCE(SUM(l.amount), 0);

-- C4 balance_after 链路断裂（前一条的 balance_after + 本条 amount ≠ 本条 balance_after）
SELECT user_id, id FROM (
  SELECT user_id, id, amount, balance_after,
         LAG(balance_after, 1, 0::bigint) OVER (PARTITION BY user_id ORDER BY created_at, id) AS prev
  FROM points_ledger
) t WHERE prev + amount <> balance_after;
```
规模变大后（流水超过千万行），C1 和 C4 改成只对「昨天有流水的用户」做增量检查。C2 和 C3 本来就只看昨天的数据。

## 安全与合规 <!-- 必填 -->
- **鉴权边界**：服务只信任网关注入的 `X-User-Id` / `X-User-Status`。生产环境必须做到：① 网关剥掉客户端上传的 `X-User-*`；② 服务只在集群内网暴露（NetworkPolicy 只放行网关）。没做到这两点就不能上线（SRE 在 08 上线单里列成阻断项）。本地自测时可以直接带这两个 header。
- **越权**：所有查询都以 header 里的 user_id 为条件，接口不接受路径或 Query 里传 user_id，所以不存在水平越权的入口。
- **个人信息最小化**：本服务只存 `user_id`（假名标识），不存手机号、设备号、IP、位置。访问日志记录 `user_id`、路径、状态码、耗时和 trace_id，**不记录** `Authorization`、Cookie 和请求体。埋点里的 `device_id` 等公共属性由客户端 SDK 上报，按现有隐私政策走，不经过本服务。
- **注销与保存期限**：账号注销后签到和流水怎么处理（匿名化还是按会计要求保留），**待法务确认**（列入待拍板）。本期不做自动删除。
- **防刷限流**：签到接口按 user_id 10 次/分钟（R10），网关和进程内都限一遍；读接口建议 60 次/分钟（网关侧）。设备级防刷延后到 P2。
- **注入和输入校验**：全部用参数化 SQL；`X-User-Id` 按白名单正则校验；`X-Request-Id` 必须是 UUID；`limit` 限制在 1–50；游标解码失败返回 400，不 panic。
- **数据完整性**：流水只追加（触发器加 GRANT），余额有 `CHECK >= 0`，三道唯一约束，加上每日对账。
- **数据库账号最小权限**：应用账号只有 `SELECT/INSERT` ledger，`SELECT/INSERT/UPDATE` account，`SELECT/INSERT` checkin_record；迁移用单独的 DDL 账号。数据库密码通过环境变量 / Secret 注入（`DATABASE_URL`），**不写进代码、产物和日志**。
- **传输**：客户端到网关全程 HTTPS；网关到服务走内网（以后再评估 mTLS）。
- **供应链**：只有一个第三方依赖 pgx，`go.sum` 入库；CI 里跑 `govulncheck`（等 Go 环境就绪后再加）；镜像的 SBOM 和签名由 SRE 在 08 按供应链安全技能包处理。
- **AI 相关**：不涉及（PRD 的 AI 机会评估结论是不用 AI）。

```go
}
```
（`civil.Date` 是 internal 包里自己定义的 `struct{Y int; M time.Month; D int}`，不引入第三方包。）

**必须有的单测**（不需要 PG 也能跑）：断签重置；第 3 天 +10；第 7 天 +30 之后第 8 天回到周期第 1 天、streak=8；同一 request_id 重放；同一天换 request_id 返回 already；100 个 goroutine 并发签同一个用户，只有 1 次成功且余额 = 10；23:59:59.999 和 00:00:00 两个时刻的判日；规则 `effective_date` 切换；游标翻页时中间插入新流水，结果不重不漏；限流第 11 次返回 429；X-User-Id 缺失返回 401；封禁用户签到返回 403、查流水返回 200。

**本机没有 Go 时的降级方案**（不擅自安装系统软件）
1. 后端照常写代码，默认构建只用标准库；PG 实现放在 `-tags pg` 后面，这样以后在任何离线的 Go 1.26+ 环境里，`go vet ./... && go test -race ./...` 都能直接跑。
2. 本机做不了编译和测试，就做静态走查：逐个函数对照本契约，走查结论写进 `06-自测记录-后端.md`，并标「**未编译、未运行**」；不允许写「测试通过」。
3. 遗留项（交 QA 和 SRE）：① 在有 Go 1.27.x 的机器或 CI 镜像 `golang:1.27` 里跑 `go test -race ./...`；② 在 PG 18 上执行迁移，跑 `go test -tags pg ./...` 和对账 SQL。
4. 如果用户希望在本机补测：可以由用户自己安装 Go（例如 `brew install go`），或者授权使用 Docker（目前还没确认本机有没有 Docker）。这些都要**用户确认后才执行**，本方案不代为安装。

**Android 实现要点**（交给客户端工程师）：一个 `CheckinRepository` 对外暴露 `StateFlow<CheckinStatus>`，首页卡片和积分页共用。签到用例的状态机按交互说明实现；`request_id` 在点击时生成，失败后重新点击要换新的，**只有超时确认后的重试才复用**同一个。onResume 时如果服务端返回的 `server_date` 和缓存里的不一样，就刷新。OkHttp 拦截器负责注入鉴权和 `X-Request-Id`，401 统一跳登录。流水用 Paging 3 的 `PagingSource<String, LedgerItem>`。触感 API（`HapticFeedbackType.ConfirmTap`）在哪个 Compose 版本里有**未核实**，没有就降级成 `View.performHapticFeedback(HapticFeedbackConstants.CONFIRM)`（API 30+）。
