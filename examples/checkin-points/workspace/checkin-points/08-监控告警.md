## SLI / SLO <!-- 必填 -->
| # | SLI（怎么量） | SLO | 窗口 | 说明 |
|---|---|---|---|---|
| S1 | **签到可用性** = 1 − 签到 `POST /api/v1/checkin` 的 5xx 请求数 ÷ 总请求数 | **≥ 99.9%**（错误预算 0.1%） | 28 天滚动；5 分钟 / 1 小时用于燃烧率告警 | 4xx（400 / 401 / 403 / 429）是客户端或身份层的结果，不计入服务端可用性，单独监控（A-11、A-12）。PRD 护栏口径是「成功或已签 ÷ 全部签到请求」，分母含 4xx，比 S1 严；该口径放在业务看板每日展示，**不拿它做页告警**，需要产品经理确认以哪个为准 |
| S2 | 签到时延：`POST /api/v1/checkin` 服务端处理耗时 | **99% 的请求 < 300 ms**（初值）；事务内部 P99 < 30 ms（05 的目标） | 5 分钟 / 28 天 | 没有基线，B4 压测后校准。客户端 10 秒超时远大于此，300 ms 是体验与容量的早期预警线，不是客户端超时线 |
| S3 | 读接口可用性：status、balance、ledger 的非 5xx 占比 | ≥ 99.5% | 28 天 | 读接口出错不直接影响资金，要求低一档 |
| S4 | 读接口时延：status P99 | < 200 ms | 5 分钟 | status 最多 8 次 SQL（D-04，修复前按此估算），阈值压测后校准 |
| S5 | **资金正确性**：每日对账异常条数（C1–C4 之和） | **= 0**（零容忍，无错误预算） | 每日 01:00 的一次运行 | PRD 护栏；任何非零都是 P0，见 F-01 |
| S6 | 对账按时完成：当日 01:30 前有一次成功运行 | 100% | 每日 | 否则 S5 的「= 0」可能只是没跑 |
| S7 | 身份边界：外部伪造 `X-User-*` 的探针必须被拒 | 100% | 持续（每 5 分钟） | 见 S-01 |

错误预算：28 天 0.1%，按 40 QPS 峰值、日均约 30 万次签到请求粗算，每天允许约 300 次 5xx。放量早期流量小，用「绝对条数 + 最小样本数」避免单个错误造成 100% 错误率误报（见告警规则的守卫条件）。

## 看板 <!-- 必填 -->
按规则 5 分三块，**不混在一起**：稳定性看板和资金护栏看板归 SRE；业务看板归数据与增长运营。

**1. 稳定性看板「checkin-points / 稳定性」（SRE 与安全工程师维护）**
| 区块 | 面板 |
|---|---|
| 入口（来自网关，独立于服务自身，服务挂了也有数据） | 四个接口的 QPS、各状态码占比（2xx / 4xx / 429 / 5xx）、网关 P50 / P95 / P99 |
| 服务 | 签到 5xx 比例与错误预算剩余（28 天）、燃烧率（1h / 6h）、各 `route` 的 P99、`result` 分布（new / replay / already / rate_limited / unavailable / internal）、panic 次数 |
| 数据库事务 | 事务耗时 P50 / P99、事务错误按原因（lock_timeout、statement_timeout、conflict、other）、连接池（已占用 / 空闲 / 上限 / 获取等待）、重复键冲突次数（23505 兜底触发次数，理论上接近 0） |
| 数据库实例 | CPU、IOPS、连接数、慢查询、锁等待会话数、存储容量（年增约 70 GB）、主备延迟（云监控） |
| 运行时 | Pod 数与重启、CPU / 内存、goroutine、GC 暂停；节点时钟偏移 |
| 发布 | 版本与 rule_version 标注（`build_info`）、放量档位标注、功能开关状态（开 / 关）。**开关关闭时整块看板顶部要有醒目标记** |

**2. 资金护栏看板「checkin-points / 资金护栏」（SRE 与安全工程师维护，对账口径来自 reconcile.sql）**
| 面板 | 说明 |
|---|---|
| 对账异常条数（C1 / C2 / C3 / C4 分开） | 每日一个点，期望恒为 0；非零标红并链接异常明细 |
| 对账最近成功时间、耗时 | 判断是否漏跑；耗时超过 10 分钟触发分区 / 增量改造（05） |
| 当日积分发放量 vs 日预算阈值 | 阈值来自 B7；未定前只画曲线不设线 |
| 当日新签到数、`points_grant` 条数、平均每次签到流水条数 | 平均应在 1.0–2.0 之间（约 1.29，05），偏离提示异常 |
| 触发器拒绝、CHECK 违反（来自数据库日志） | 期望恒为 0 |

**3. 业务看板（数据与增长运营维护，放在 11-数据看板，不在本文范围，不挂告警）**
数据源是神策里的服务端事件，不是 Prometheus：日签到率（北极星）、次日签到率、7 日连签达成率、签到漏斗（曝光 → 点击 → 服务端成功）、断签率、积分发放总量与人均、积分页 UV / 翻页深度。这里只约定**口径入口**：`checkin_success` 是唯一的签到口径（事务提交后才打，`already` 与重放不打），`points_grant` 是发放口径，两者与对账结果交叉核对；若神策与表数据不一致，**以表为准**（05）。业务指标掉了，找产品经理和数据与增长运营，不找值班 SRE（规则 5）。

## 告警规则 <!-- 必填 -->

### 对账 CronJob 方案（B3，待用户确认后落地）
- 调度：每日 01:00 北京时间（`schedule: "0 1 * * *"`，`timeZone: "Asia/Shanghai"`；CronJob 的 `timeZone` 字段需要 Kubernetes 版本支持，集群版本未核实，不支持就改成换算后的 UTC 17:00 并写明）。`concurrencyPolicy: Forbid`，`startingDeadlineSeconds` 设为 1800，`backoffLimit` 设为 0（失败由告警处理，不要静默重跑掩盖问题）。
- 账号：只读账号（SELECT），密码来自 Secret；优先连只读副本（若有），避免 C1 / C4 的全表扫描影响主库。
- 执行：包装脚本依次执行 `server/scripts/reconcile.sql` 的四个查询，统计每一项的行数，异常明细（只含 user_id、记录 id、金额，不含其他个人信息）写到作业日志，行数与最近成功时间推送到 Pushgateway（`reconcile_anomaly_rows{check}`、`reconcile_last_success_timestamp_seconds`、`reconcile_duration_seconds`）；任一项非零则以非零码退出。
- 补跑：C3 只看「昨天」，某天漏跑后那天的漏发不会被补查。包装脚本要支持传入日期参数，F-02 触发后按缺失日期补跑 C3；C1、C4 是全量，不受漏跑影响。
- 验收：B2 里人为注入 C1–C4 异常（测试库，需要临时禁用触发器，只在测试库）能被检出，才能说「对账为 0」有意义（07 的经验）。

### /metrics 口径（P-07 结论）
**结论**：采用自研零依赖的 **Prometheus 文本格式**（计数器 + 固定桶直方图），由后端工程师在 `server/` 实现；指标名和标签对齐 OpenTelemetry 的语义，全量稳定后再评估换成 OTel SDK（OTel 是技术雷达的采用项，CR P-07 允许合并过去）。**不采用 expvar**：05 设想的 expvar 输出是 JSON，Prometheus 不能直接抓取，要再加一层 exporter，得不偿失。

**暴露方式**：独立端口（新增环境变量 `METRICS_ADDR`，建议 `:9090`），**不挂在业务端口，不经过网关**，NetworkPolicy 只放行监控命名空间。不鉴权，靠网络隔离。

**指标清单**（标签只允许下列值，**禁止把 `user_id`、`request_id`、`trace_id` 放进标签**，否则基数爆炸，也有隐私问题）
| 指标 | 类型 | 标签 | 用途 |
|---|---|---|---|
| `checkin_http_requests_total` | counter | `route`（只取注册的路由模式：`GET /api/v1/checkin/status`、`POST /api/v1/checkin`、`GET /api/v1/points/balance`、`GET /api/v1/points/ledger`、`other`）、`status`（HTTP 状态码） | 可用性（S1、S3）、5xx、429、401、403 |
| `checkin_http_request_duration_seconds` | histogram | `route`；桶 0.005、0.01、0.025、0.05、0.1、0.25、0.5、1、2、5 | 时延（S2、S4） |
| `checkin_result_total` | counter | `result` = `new` / `replay` / `already` / `restricted` / `rate_limited` / `invalid_request` / `unavailable` / `internal` | 业务结果分布；`new` 的次数应等于 `checkin_success` 事件数 |
| `checkin_points_granted_total` | counter | `type` = `CHECKIN_BASE` / `CHECKIN_STREAK_BONUS`；值累加积分数 `amount` | 日发放量与预算（F-04）；只在事务提交成功后累加 |
| `checkin_tx_duration_seconds` | histogram | 无；桶 0.005、0.01、0.02、0.03、0.05、0.1、0.25、0.5、1、3 | 事务 P99 < 30 ms 的目标 |
| `checkin_tx_errors_total` | counter | `reason` = `lock_timeout`（SQLSTATE 55P03）/ `statement_timeout`（57014）/ `conflict`（23505 兜底触发）/ `unavailable` / `other` | 锁等待、库不可用 |
| `checkin_db_pool_*` | gauge / counter | 无 | 来自 `pgxpool` 的统计（已占用、空闲、上限、获取次数、需要等待的获取次数、累计等待时长）；字段以实际 pgx v5 版本为准，未核实 |
| `checkin_ratelimit_rejected_total` | counter | 无 | 进程内限流拒绝次数（与网关 429 对照，D-05） |
| `checkin_panic_recovered_total` | counter | 无 | recover 次数（A-07） |
| `checkin_unknown_user_status_total` | counter | 无 | P-08 的 warn 对应计数（A-16） |
| `checkin_build_info` | gauge（恒为 1） | `version`、`rule_version`、`store`（`postgres` / `memory`） | 看板标注；`store="memory"` 出现在生产要立即告警（会丢数据） |
| Go 运行时与进程标准指标 | — | — | goroutine、内存、GC、文件描述符 |

**实现要点与验收（给后端工程师，SRE 不改业务代码）**
1. 在最外层中间件统计 `checkin_http_requests_total` 与时延，`route` 取 mux 匹配到的模式，未匹配归 `other`，避免用原始路径当标签。
2. 事务错误按 SQLSTATE 映射；`checkin_result_total` 与 access 日志、`checkin_success` 事件的计数交叉一致。
3. 有单测：用假 Store 返回 `ErrUnavailable` / `ErrConflict`，断言计数器变化；`/metrics` 不出现 `user_id`。
4. **过渡替代**（只允许 G0、G1 使用）：`/metrics` 未就绪时，用网关指标和 access 日志（`status`、`dur_ms`）在日志平台里做日志指标，业务计数用 `event=checkin_success` / `points_grant` 日志；但 `reason`（锁超时）等信息日志里没有，所以**G2 市场放量前必须有 `/metrics`**。
5. 日志里不要出现 Authorization、Cookie、请求体、`DATABASE_URL`；access 日志保留 `user_id`（假名），保留期限待隐私合规确认。

### 处理手册（RB，文字版）
所有会改线上状态的动作（关开关、回滚、摘路由）按上线单执行；P0 事件需要用户预授权（上线单待拍板第 3 项）。**任何手册都不包含删除数据、禁用触发器、修改流水或余额。**

- **RB-01 签到 5xx / 可用性燃烧（A-01、A-02、A-03、A-07）**：①看板确认是 500 还是 503；500 = 非预期（事务已回滚，不会多发），查 panic 与错误日志；503 转 RB-03。②看是否刚发布或刚放量，是则先暂停放量。③10 分钟内无明确原因且仍在烧：关入口（SW-1），再决定回滚代码（上线单回滚步骤 3）。④确认无资金影响：关入口后手动跑一次对账。⑤通知总控、后端工程师。
- **RB-02 时延（A-04、A-05、A-06）**：①对比事务耗时与整体耗时，判断是 DB 还是应用。②查 DB CPU、慢查询、锁等待；status 慢先看 D-04（逐格查库）。③流量异常则转 RB-04。④必要时扩容实例（经用户确认）或暂停放量；时延告警不触发回滚，除非伴随 5xx。
- **RB-03 数据库锁、连接、503（A-08、A-09、A-10）**：①`pg_stat_activity` 看谁持有锁、持续多久；同一用户的并发会排队，不同用户之间没有锁竞争，所以大面积锁超时说明有长事务或慢事务。②连接数接近上限先看是否有泄漏 / 对账 Job 占连接。③库不可用走云厂商故障流程；服务端 503 会让客户端换新 id 重试，**不会多发**（A2）。④不要重启数据库、不要 kill 会话，除非用户确认。
- **RB-04 429 / 401 / 403 / 未知状态（A-11、A-12、A-16、S-03）**：①429 突增：先看是不是客户端 bug（重试风暴）或单用户刷量；单用户则在网关封该用户的签到请求（经确认）；多用户则联系客户端工程师暂停该版本放量。②401 突增：查网关 token 校验、账号服务；服务本身不解析 token。③`X-User-Status` 出现未知值：联系网关 / 账号负责人确认新增状态，服务端按「受限」处理，需后端补充枚举（契约澄清，不改字段）。④S-03 疑似刷量：保留日志交安全评审。
- **RB-05 对账异常 / 流水被动 / 余额约束（F-01、F-05、F-06）**：P0。①**不要修数据、不要禁用触发器、不要回收积分。**②关发分（SW-1）冻结继续扩大，暂停 Android 放量。③保留现场：对账作业日志、对应时间段的 access 日志和 `checkin_success` / `points_grant` 事件、数据库日志；通知后端工程师和架构师。④按 C1–C4 判断类型：C1 余额与流水和不一致、C2 同日重复基础奖励、C3 签到记录与流水金额不符、C4 balance_after 链路断裂；先排除误报（P-05 / P-06 修订口径）：用 `checkin_record.checkin_date` 对照确认是否真错。⑤确认是真错发后，补偿方案另出（`ADJUST` 补偿流水，业务方 / 财务评审，用户确认），SRE 不自行动手。
- **RB-06 对账没跑 / 太慢（F-02、F-03）**：①看 CronJob 与最近一次 Job 日志、Pushgateway 指标。②手动补跑一次（只读账号），C3 带日期参数补缺失日期。③耗时超 10 分钟：提交增量检查 / `points_ledger` 分区的改造需求（05 的演进方案）。
- **RB-07 积分预算（F-04）**：①80%：通知产品经理、业务方，确认是否正常（活动、放量）。②100%：暂停放量，提请总控决定是否关发分；关发分会让用户看到「签到失败」，需要产品与客服口径。③积分发放不回收。
- **RB-08 header 伪造 / 绕过网关（S-01、S-02）**：P0。①立即在网关摘掉全部路由（不只是签到），因为伪造可以读他人余额和流水，也可能冒充签到。②保留网关与服务的 access 日志，按 `user_id` 与时间段排查可疑访问。③检查网关配置是否被回滚、是否有新增路由漏了 header 剥离；检查 NetworkPolicy 是否被改。④修复并复测 TC-40 / 41 后才恢复；通知总控与安全负责人，必要时评估是否需要告知受影响用户（法务）。
- **RB-09 实例、就绪、采集中断（A-13、A-14）**：①`kubectl describe` / 事件看就绪失败原因：`/readyz` 失败多半是数据库连不上（转 RB-03）。②OOM 则按内存曲线调限制（经确认）。③采集中断是「盲飞」：恢复前暂停放量，不在看不见的情况下继续发。
- **RB-10 时钟偏移（A-15）**：①检查节点 NTP 服务与云厂商时间源。②偏移 > 1 秒时在零点前后 30 分钟特别留意 `already_checked_in` 与跨天判日异常。③修复后复核当日签到日期分布。

## 遗留与经验
**遗留（需要别人给的东西）**：①值班人员姓名、电话、渠道；②日预算数值（B7）；③网关的具体实现与是否支持直接响应 / JWT 注入 header；④集群版本与 CNI 是否执行 NetworkPolicy；⑤`/metrics` 与开关代码（后端工程师）；⑥PRD 的「成功率」口径是否改成与 S1 一致（产品经理）。

**经验条目（供复盘回流技能包）**
- 更好的做法：资金类服务的「对账 = 0」要配「对账没跑」的告警（死人开关），否则 0 可能只是没执行。
- 更好的做法：Prometheus 没法直接抓 expvar 的 JSON；零依赖的服务要直接输出 Prometheus 文本格式，别先写 expvar 再想办法接。
- 更好的做法：早期灰度流量小，错误率告警必须带最小样本数 / 绝对条数守卫，不然一个错误就是 100%。
- 踩坑：监控口径（P-07）拖到 08 才定，导致指标没法在 06 同步落代码；技术方案里应该把「要暴露哪些指标」写成验收项。
