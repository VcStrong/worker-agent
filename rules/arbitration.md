# 交界处摩擦的仲裁规则（REQ-007）

> 来源：图谱「05 交界处的六个高频摩擦」，角色名已换成合并后的专家（项目经理 / 发布经理 → 总控；研发负责人 / 技术负责人 / 研发经理 → 架构师；UI / 设计系统负责人 → 体验设计师；运维 / SRE / 基础架构 → SRE 与安全工程师；产品与增长团队 → 产品经理、数据与增长运营）。
> 所有 agent 共用。角色之间有分歧时由**总控**按下列规则裁决，裁决结果写进 `workspace/<需求名>/log.md`。
> **规则覆盖不到的分歧：总控升级给用户拍板（有知识库时走 kb_ask），不自行编造规则。**

## 规则 1　需求能不能中途改

- 产品经理有权调整优先级；但**已经排进版本**（进入 03 方案排期之后）的需求要改，必须同时拿到**总控**（排期影响）和**架构师**（工作量影响）两个角色的确认后才执行。
- 变更必须写成三段，落在 PRD 的「范围」或变更记录里，不接受口头一句「这个简单」：
  - **改动内容**：
  - **影响范围**：（哪些产物、哪些角色、哪些接口要跟着改）
  - **延后哪一项**：（为了这个变更，哪项需求延后或砍掉）
- 开发阶段（06）出现变更：总控先暂停受影响角色，拿到两方确认后再把变更交给下游；变更影响已拍板的内容（PRD 范围或接口契约）时，回到对应拍板节点请用户确认。

## 规则 2　设计还原度算不算缺陷

- 主流程错、组件规范被破坏、间距在栅格体系外 → **算缺陷**，走缺陷流程（测试报告的缺陷清单）。
- 像素级偏差、非关键状态下的间距浮动 → 归**设计走查清单**（05 视觉标注说明「走查清单」节），一次性收敛，不进缺陷列表。
- 判断标准的解释权在**体验设计师**，不在工程角色和测试专家之间拉锯。

## 规则 3　排期是谁给出的承诺

- 工程角色和架构师给的是「评估」，**总控**给的是「承诺」，两者必须分开写。
- 对外同步（给用户）的日期只能由评估人确认过的版本签发；不绕过评估角色直接承诺日期。
- 在 AI 团队里「排期」指阶段顺序和调用预算（max_calls），承诺时同时写明预计调用次数。

## 规则 4　缺陷该谁修

- 按「**谁引入谁修**」定责任角色，按「复现路径落在哪个模块」定归属（前端 / 客户端 / 后端 / AI 应用…）。
- 环境不通、配置缺失、依赖库版本冲突 → 指派 **SRE 与安全工程师**，不算业务缺陷。
- **测试专家**负责给出可复现路径，不负责替开发定位代码；也不擅自改被测业务代码。
- 大模型输出质量问题（幻觉、拒答、不合规）→ 先由 **AI 评测与安全合规专家**定性，再按引入者指派给 AI 应用 / Agent 工程师或模型与算法工程师。

## 规则 5　指标掉了算谁的

- 增长类指标（DAU、转化、留存、渗透率）→ **产品经理**、**数据与增长运营**。
- 稳定性指标（可用性、错误率、时延、发布失败率）→ 对应**工程角色**与 **SRE 与安全工程师**。
- AI 效果指标（准确率、有用率、幻觉率、单次成本）→ **AI 产品经理**（目标）与 **AI 应用 / Agent 工程师**（实现），评测口径归 AI 评测与安全合规专家。
- 两套看板分开挂（10 监控告警规则、11 数据看板），告警阈值和值班人写清楚。

## 规则 6　谁能决定上线窗口

- **总控**统一维护发布日历，避开大促、业务高峰、节假日前和无人值守时段。
- 窗口之外的紧急发布，需要**架构师**与 **SRE 与安全工程师**双签，并附回滚预案。
- 灰度比例、放量节奏由 SRE 与安全工程师和对应工程角色共同定；**产品经理**只对「要不要全量」表态。
- 上线放量是拍板节点：最终由用户确认（approval_mode=auto 时按建议执行并记录理由）。
- 任何发布、部署、推送操作都只出方案，用户确认后才执行。
