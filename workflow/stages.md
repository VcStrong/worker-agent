# 九阶段流程与阶段门禁（REQ-005）

> 来源：图谱「01 流程主干」+「03 阶段×角色矩阵」，主导角色已换成 14 个专家或总控。
> 总控按本文件判断：上一阶段**必交产物**缺失时不进入下一阶段，并提示缺什么；用户指定从某阶段开始时，先校验该阶段**准入条件**。
> 每个阶段结束写阶段小结 `workspace/<需求名>/<阶段序号>-阶段小结.md`（结论、产物清单、遗留问题）。
> 产物路径：`workspace/<需求名>/<阶段序号>-<产物名>.md`；模板见 `templates/deliverables/`；用 `python3 scripts/validate.py --deliverable <文件>` 校验。
> 拍板节点（只有 3 个）：🟥 立项（02 结束）、🟥 技术方案（05 结束）、🟥 上线放量（08 灰度放量前）。

## 01 战略洞察

- **主导**：产品经理（兼产品负责人、用户研究员）
- **准入**：有一个方向性问题（做不做、为谁做），或用户要求做市场 / 竞品研究。
- **准出**：洞察报告结论明确（做 / 不做 / 先验证什么）；用户证据有来源。
- **必交产物**：`01-洞察报告.md`（01-insight-report）
- **可跳过**：需求已明确的功能需求直接从 02 开始。

## 02 需求立项　🟥 拍板节点：立项

- **主导**：产品经理；**AI 产品经理**每个需求都参与，填 PRD「AI 机会评估」
- **准入**：需求原文（一句话需求也可以）；有知识库时先 kb_search / kb_iteration 读本期资料。
- **准出**：PRD 必填节齐全；每个用户故事有验收标准；异常态写全；埋点与指标口径已定义；「AI 机会评估」有结论（用 / 不用 AI 及理由）；**用户拍板通过**。
- **必交产物**：`02-PRD.md`（03-prd）

## 03 方案排期

- **主导**：总控（兼项目经理）
- **准入**：PRD 已拍板。
- **准出**：执行计划（阶段 × 角色 × 产物）确定；最少角色自检完成；并发任务和调用预算（max_calls）明确；风险清单。
- **必交产物**：`03-执行计划.md`（小需求）或 `03-路线图.md`（02-roadmap，多版本需求）

## 04 交互设计

- **主导**：体验设计师（兼交互、UI / 视觉、设计系统）
- **准入**：PRD 已拍板。
- **准出**：主流程和全部状态（含异常态）有说明；多端差异写明；视觉改动有标注和走查清单。
- **必交产物**：`04-交互说明.md`（04-interaction-spec）；有视觉改动时 `04-视觉标注.md`（05-visual-spec）
- **可跳过**：纯后端 / 数据需求。

## 05 技术方案　🟥 拍板节点：技术方案（接口契约锁定）

- **主导**：架构师（兼基础架构、研发经理、技术总监）
- **准入**：PRD 已拍板；涉及界面时交互说明已完成。
- **准出**：项目现状（技术栈和版本）已探测；选型及成熟度表完整（「评估」项不进生产实现，「试用」项有风险和回退）；接口契约、数据模型、容量与成本、安全与合规、任务拆分写全；**用户拍板通过**。
- **必交产物**：`05-技术方案.md`（06-tech-design）

## 06 开发联调

- **主导**：对应端的工程角色——前端工程师 / 客户端工程师 / 后端工程师；涉及大模型时 AI 应用 / Agent 工程师。互相独立的端**可以并发**（≤ max_parallel），同一角色多实例记为 `角色#序号`。
- **准入**：技术方案已拍板（接口契约锁定）；目标仓库是 git（不是就先 git init + 初始提交，不加 remote、不 push）。
- **准出**：代码已改并通过自测；自测记录列出改动文件；接口没好时有可一键切换的 mock；架构师 Code Review 通过。
- **必交产物**：`06-自测记录-<端>.md`（07-mr-selftest，每端一份）

## 07 测试保障

- **主导**：测试专家（兼测试开发）；涉及大模型 / 个人信息 / 生成内容时 **AI 评测与安全合规专家**填「AI 评测与合规」节。
- **准入**：所有端的自测记录已交；提测范围明确。
- **准出**：P0 / P1 缺陷清零；核心用例 100% 通过；遗留问题有负责角色；准出结论为「通过」。
- **必交产物**：`07-测试报告.md`（08-test-report）

## 08 发布上线　🟥 拍板节点：上线放量

- **主导**：SRE 与安全工程师（精简档由架构师出方案）
- **准入**：测试报告准出为「通过」。
- **准出**：上线单含灰度计划、回滚方案、上线窗口和检查清单；监控告警规则就绪；**用户确认放量**。部署 / 发布 / 推送命令只出方案，用户确认后执行。
- **必交产物**：`08-上线单.md`（09-release-plan）、`08-监控告警.md`（10-monitoring，小改动可并入上线单「检查清单」）

## 09 运营复盘

- **主导**：数据与增长运营（兼数据分析、各类运营、客服）
- **准入**：已上线（或样例流程到发布方案为止时，用上线方案中的指标预期做复盘）。
- **准出**：指标结果与原因分析；经验条目已交总控整理进 `proposals/lessons-<需求名>.md`。
- **必交产物**：`09-复盘报告.md`（11-dashboard-retro）

## 部分流程（总控按需求裁剪）

| 需求类型 | 走哪些阶段 |
|---|---|
| 全新功能 | 02 → 03 → 04 → 05 → 06 → 07 → 08 →（09） |
| 已有 PRD | 校验 02 准出 → 从 04 或 05 开始 |
| 修线上 Bug | 06 → 07 → 08（小 Bug 可只出自测记录 + 上线单） |
| 纯技术改造 | 05 → 06 → 07 → 08 |
| 运营活动 | 02 → 04 → 09 |
